# Требования статьи и выбранные образцы

До первого черновика автор получает короткое задание с требованиями владельца
и отрывками старых материалов. Наличие статьи в архиве не означает, что модель
её прочитала. Native runner сохраняет этот пакет и повторяет его в `next`,
при исправлении и в `continue-research`.

## Подготовка

1. Собери действующие требования из запроса и последующих замечаний. Сохрани
   область применения: запрет термина для одной стратегии не становится запретом
   для всех игр. Новое уточнение владельца заменяет прежнее противоречащее ему.
2. Прочитай указанные владельцем гайды. Если их нет, найди близкий материал
   той же игры и жанра. Для BG используй `corpus-bg`/`corpus-archive` либо MCP;
   не подставляй гайд по обычной колоде из общего `corpus`.
3. Выбери до четырёх коротких дословных отрывков, каждый с ясной задачей:
   объяснение выбора, переход, сравнение сборок, начало или заключение.
   В `use_for` назови полезный приём, в `avoid` — что нельзя переносить.
   Не копируй обороты механически и не превращай пример в шаблон каждого абзаца.
4. Зафиксируй пакет командой `context`. Если подходящий источник недоступен
   или образец не нужен для этой правки, оставь список пустым и объясни причину
   в `style_note`. Нельзя писать, что старые гайды учтены, если отрывков нет.
5. До черновика добавь `article_plan` по [порядку объяснения](ARTICLE_STRUCTURE.md):
   вопрос читателя, главный ответ и вклад разделов с зависимостями и claim IDs.
   Этот план также сохраняется в context и проверяется при допуске.

`author-context.json` — рабочий файл агента, не форма для пользователя:

```json
{
  "schema_version": 1,
  "profile": "battlegrounds-guide",
  "article_plan": {
    "reader_question": "Какое решение объясняет статья?",
    "main_answer": "Ответ с существенным условием из исследования.",
    "sections": [{"id": "decision", "question": "Когда применим совет?", "contribution": "Условие и граница решения.", "depends_on": [], "claim_ids": ["CLM-1"]}]
  },
  "requirements": [
    {
      "id": "reader-value",
      "instruction": "Объясняй подтверждённые решения и их цену; не пересказывай очевидный эффект карты."
    },
    {
      "id": "magnet-term",
      "instruction": "В этом гайде не называй носителя магнетизма стеком.",
      "forbidden_literals": ["стек", "стека", "стеку", "стеком", "стеке"]
    }
  ],
  "style_note": "Здесь укажи выбранные приёмы или конкретную причину отсутствия образцов.",
  "style_examples": []
}
```

Каждый элемент `style_examples` содержит `id`, `profile` (точно как у запуска),
`source` (URL или понятное происхождение), `source_path` (локальный UTF-8 файл),
`source_sha256` (хеш его байтов), `quote` (дословный отрывок до 2000 символов),
`use_for` и `avoid`. Относительный путь считается от JSON-файла. До сохранения
helper проверяет хеш и присутствие цитаты в файле. Запуск хранит отрывок внутри
себя: удаление рабочего JSON или изменение архива не меняет уже выданный образец.
Сохраняй исходники и пакеты конкретных статей в ignored `build/`, не в Git.
В примере плана `CLM-1` замени реальным claim ID; обязательные claims handoff
должны быть покрыты. Если разделов несколько, задай вклад каждого отдельно.

```powershell
python teams/manacost-publish/scripts/publish.py context RUN --artifact author-context.json
python teams/manacost-publish/scripts/publish.py next RUN
```

В переносимом manacost-publish путь — `scripts/publish.py`; в editor-team:
`PYTHONPATH=python python -m editorteam.publication_run context RUN --artifact FILE`.
Для meta-report после `prepare` есть собственная команда:
`python skills/meta-report/scripts/meta_report.py context RUN --artifact FILE`.

После нового замечания обнови пакет целиком, сохрани прежние действующие пункты
и снова вызови `context`. Это сбрасывает допуск старых отзывов, сохраняя их
историю и прежний экспорт. Не редактируй `state.json` и снимки в `artifacts`.
Повторная передача того же пакета ничего не сбрасывает. Старый запуск можно
прочитать без пакета, но до следующего draft/review/export он должен быть задан.

## Проверка исполнения

Автор получает требования в начале задания, затем примеры с их назначением.
Литературный reviewer получает те же примеры и проверяет каждое требование:

```json
{
  "author_context_sha256": "хеш из next",
  "requirement_checks": [
    {"id": "reader-value", "status": "met", "quote": "Точная цитата из новой статьи", "reason": "Как этот фрагмент выполняет требование"}
  ],
  "style_checks": []
}
```

Это дополнительные поля полного литературного отзыва. Нужна одна строка на
каждый id требования и образца, без пропусков. `not_met` блокирует допуск;
`not_applicable` требует конкретной причины неприменимости, а не разрешения
проигнорировать неудобное требование. Для отсутствующего приёма укажи проверенный
фрагмент и объясни охват. `met` требует точной цитаты из текущей статьи.
Фактологический reviewer получает требования и хеш пакета, но не старые примеры;
он возвращает `author_context_sha256` вместе с обычным отзывом.

Прямые запреты из `forbidden_literals` проверяются также программой во всём
тексте, включая заголовки и подписи, при draft/revise/review/export. Это поиск
явно перечисленных слов или фраз, без морфологии и оценки смысла. Содержательность,
точность сравнения с образцом и обоснованность `not_applicable` оценивает reviewer.
Наличие цитаты само по себе не доказывает хорошую прозу или верный вывод.

Выбор архивного отрывка для задачи не меняет его статус в корпусе, не одобряет
обучающий пример и не подтверждает актуальность игровых советов. Старые тексты
служат форме; факты приходят из research. Прежний `next --example-bank` остаётся
разовым дополнением для одобренных before/after-примеров; он не заменяет этот
сохранённый пакет и не даёт автоматического доступа к старым гайдам.
