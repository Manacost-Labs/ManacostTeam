# Порядок объяснения и логика статьи

До прозы реши, на какой вопрос отвечает материал, что читатель уже знает и
какой вывод должен понять. Затем выстрой объяснение: какие предпосылки нужны
для первого решения и что следующий раздел добавляет к уже сказанному.
Оглавление исследования само по себе не задаёт хороший порядок чтения.

## План автора

Для новой статьи в native runner сохрани `article_plan` внутри author_context:

```json
{
  "reader_question": "На какой вопрос читателя отвечает материал?",
  "main_answer": "Главный ответ с необходимым ограничением.",
  "sections": [
    {
      "id": "entry",
      "question": "Что нужно понять до выбора действия?",
      "contribution": "Условия, от которых зависит дальнейшее решение.",
      "depends_on": [],
      "claim_ids": ["CLM-1"]
    },
    {
      "id": "choice",
      "question": "Как эти условия меняют выбор?",
      "contribution": "Применение уже объяснённых условий и граница совета.",
      "depends_on": ["entry"],
      "claim_ids": ["CLM-2"]
    }
  ]
}
```

Пример показывает поля, а не обязательные два раздела или готовую композицию.
Замени вопросы и claim IDs содержанием конкретного handoff. Используй только
его утверждения; все обязательные claims должны найти место в плане.
План не дополняет источники фактами. Заголовок главы исследования не обязан
стать заголовком статьи. Для лёгкой вычитки сохраняй удачную композицию:
отдельный план в обычном сервисе редактуры не обязателен.

Программа проверяет уникальность разделов и ссылки на уже объяснённые
предпосылки. При смене композиции обнови план командой `context`; старые отзывы
теряют допуск. План сохраняется при продолжении вместе с требованиями владельца.
Новый handoff требует заново сверить claim IDs. Старые запуски читаются, но
черновик, новая правка и допуск требуют текущий план и полную проверку структуры.

## Чтение готового текста

Проверь статью в порядке читателя, до полировки отдельных фраз:

- Вступление задаёт предмет и обещает только тот разбор, который есть дальше.
- Термин, условие или причина объяснены до совета, который без них непонятен.
  Краткий анонс будущего объяснения допустим; не выдавай его за готовое решение.
- Каждый раздел отвечает на свой вопрос. Повтор может служить сравнению,
  напоминанию или навигации, но должен иметь понятное назначение.
- Между соседними блоками есть содержательная связь. Слово «поэтому» не
  подтверждает причинность. Если основания нет, нужен источник, оговорка или
  изменение вывода, а не более гладкая связка.
- Разные рекомендации сопоставлены при одинаковых условиях. Смена стадии
  партии, сборки или цели может объяснить отличие; эту смену должен видеть читатель.
- Местоимения и сравнения имеют ясный предмет. Условие и исключение не потерялись
  после перестановки. Концовка отвечает на исходный вопрос без нового совета,
  который нигде не был обоснован.

Не превращай этот список в одинаковые заголовки и абзацы каждой статьи.
Не добавляй служебные фразы ради переходов. План, id и отчёт проверки остаются
в рабочих файлах; читателю нужен сам разбор.

## Проверяемый охват

Native `next` и обычный critic получают `structure_assignment`: упорядоченные
блоки исходного текста, их id и хеш статьи. Это границы исходника, а не
автоматическое определение «правильного абзаца». Учитываются Markdown-заголовки,
пункты списков, абзацы, HTML-блоки и fenced code. Вложенный пункт с отступом
больше трёх пробелов остаётся вместе с родительским блоком. Ничего не усекать:
при превышении 256 блоков helper сообщает предел вместо неполного допуска.

Поле `structure_review` содержит тот же article_sha256, reader_question,
main_answer, order_reason, ending_reason и blocks — по одной строке на каждый
id в исходном порядке. В строке нужны quote из этого блока, function,
new_information, link_to_previous, depends_on, repeat_of, repeat_reason,
status (`clear`, `issue`, `unverified`) и reason. Пустые списки — `[]`.
Зависимость и намеренный повтор указывают на предыдущие блоки. Для повтора
объясни его отдельную функцию; точный повтор слов сам по себе не ошибка.
У heading, кода или схемы оцени роль в объяснении, не требуй полноценного
абзаца игровой прозы внутри каждого элемента разметки.

Пропуск середины, цитата из другого блока, старый хеш, повтор id, будущая
предпосылка и нерешённая проблема блокируют допуск. В native литературный
отзыв также содержит `plan_checks`: `{id,block_ids,status:clear|issue,reason}`
по каждой секции плана. Он показывает, где в статье дан запланированный ответ;
в block_ids включаются все необходимые части ответа. Всё необходимое объяснение
предпосылки должно завершиться до зависимого совета; позднее необязательное
напоминание описывается через repeat_of, а не как недостающая часть предпосылки.
Несколько вопросов могут раскрываться в одном блоке. Ошибочный план нужно
пересмотреть, а не оправдывать. Содержательную правильность связи и оснований
оценивает редактор; программа проверяет охват и согласованность ссылок.

Для ручного BG-сценария передавай тот же план и разбор явно. Его `check`
остаётся диагностикой оформления, а не допуском по логике статьи.
