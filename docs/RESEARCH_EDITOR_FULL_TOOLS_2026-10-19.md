# Сноски, длинные абзацы и полный Windows toolchain

Дата: 19 октября 2026. Модуль: `editor`. База — `9e9a6b6`.
Исправления: `f73f686` и `fe94f42`. Все сырые материалы и результаты
хранятся локально в игнорируемом `build/`; тексты статей не добавлены в Git.

## Поведение

Литеральные маркеры сносок со звёздочкой и неразрывным пробелом защищены
от превращения в Markdown-список. Экранированная звёздочка считается тем же
маркером. Проверяются число звёздочек и ссылки `[^id]`; код и экранированные
примеры не создают ложные сноски. Регулярное выражение маркеров списков
больше не поглощает пустые строки.

Защищённые сильные фрагменты обычной прозы допускают новое разбиение
абзацев с теми же словами. Изменённые слова по-прежнему требуют точного
объяснения critic. Writer и repair сохраняют полезную локальную редактуру
и исправляют конкретное нарушение, не откатывая весь длинный абзац.

Первый полный живой прогон выявил второй источник потери редактуры:
`ValidateImprovements` схлопывал абзацы и возвращал исходник даже после
одобрения critic. Дополнительная поправка принимает структурное доказательство
с точными цитатами только для обычной прозы, неизменной последовательности
слов во всём тексте, новых границ между предложениями и сохранения всех
старых границ. Цитата должна однозначно указывать на одно место, включая
перекрывающиеся повторения. Случайные пробелы, одинарные переводы строк,
перестановки, код, списки, HTML, инициалы и короткие сокращения не подходят.
Смысловые пороги и предел попыток не ослаблены.

Этот структурный механизм намеренно консервативен: короткое слово перед
точкой, повторяющаяся цитата или разметка могут дать отказ. Словесная
редактура проходит прежнюю проверку token diff. Проверка формы доказательства
не заменяет смысловую оценку critic или редактора.

## Пять инструментов действительно работают

| Инструмент | Установленная версия | Реальная проверка |
| --- | --- | --- |
| Natasha / Razdel | 1.6.0 / 0.5.0 | Полная морфология и лемматизация, не fallback |
| Hunspell | 1.7.5, русский словарь 1.0.8 | Русская опечатка и корректная подсказка |
| LanguageTool | 6.6, Temurin JRE 21 | Русский повтор слова через `/v2/check` |
| Vale | 3.17.0 | Findings редакторских правил проекта |
| Markdownlint CLI | 0.49.1 | Реальные ошибки уровней и оформления заголовков |

Установка закреплена SHA256 архивов и lock-файлами. Runtime находится в
`build/editor-windows-tools/`, без глобального PATH и автозапуска. Natasha
использует отдельный Python 3.12; HTTP-сервисы слушают только loopback.
Два native launcher запускают настоящие Hunspell и Markdownlint, сохраняя
вывод и exit code. Они решают ограничения Windows `.cmd`, путей словаря
MinGW и явной UTF-8 кодировки, не подменяют результаты проверок.

Запуск в PowerShell из корня репозитория:

```powershell
. ./editor/tools/Start-EditorTools.ps1
./editor/tools/Start-EditorTools.ps1 -Action Status
python editor/tools/windows_toolchain.py check
```

Первая команда запускает сервисы и импортирует пути анализаторов в текущий
PowerShell. Gateway и Python-анализатор нужно запускать из этого окружения.
После перезагрузки сервисы запускаются этой же командой. Полная инструкция
установки — [editor-toolchain.md](../editor/docs/editor-toolchain.md).

Проверены 7/7 анализаторов через gateway, реальные findings каждого внешнего
инструмента, отказ при остановке обязательных сервисов и восстановление
после запуска. Неполная проверка возвращает исходник при
`EDITOR_ALLOW_UNAVAILABLE=false`. Работающий анализатор не доказывает
правильность игровых фактов и не исключает ложных редакторских сигналов.

## Живые сравнения

Оба опыта используют те же 10 замороженных фрагментов Manacost и те же
запросы, что и предыдущий опыт. Это ранее виденная диагностическая выборка,
не случайная выборка и не unseen holdout. Проверяются фрагменты, не целые статьи.

В обоих вариантах каждого опыта: Claude Sonnet 5.5 через действующую Claude
CLI-подписку, effort medium, одинаковые stage token limits, retrieval off,
одинаковый полный комплект локальных анализаторов, AllowUnavailable=false.
Поле reasoning_effort gateway не управляет CLI bridge: фактическое значение
задаётся аргументом `--effort medium`. Seed и temperature CLI не фиксируются.
Исходники, диапазоны и SHA256 проверяются. Сырые запросы/ответы и все попытки
repair сохранены; отклонённый черновик никогда не показан как итоговый текст.

Первый опыт: `build/live-manacost-full-tools-2026-10-19/`, `9e9a6b6` → `f73f686`.
20/20 HTTP 200, checks_complete=true во всех ответах, 137 model calls.
Старая версия: 5 edited, 3 unchanged, 2 rejected; новая: 8 edited,
1 unchanged, 1 rejected. Два слепых модельных review согласились на одном
преимуществе новой версии и семи ничьих; на двух материалах разошлись.
Каждый отдельно выбрал 1 новую, 1 старую и 8 ничьих, но старую выбрали
на разных материалах. Общий выигрыш не доказан. Обнаруженный отказ standard
сохранён в результатах и послужил основанием для отдельной Go-поправки.

Причинная проверка дополнительной поправки: исходный standard и все семь

Таким образом, выигрыш у старого редактора не равен улучшению исходного текста.
Точечное исправление потери абзацев подтверждено и свежим прогоном, и replay;
универсальное улучшение всей редактуры этим опытом не доказано.

Остаточные ограничения: анализаторы дают не только полезные находки. В этом
опыте MD047 о завершающем переводе строки и общий терминологический сигнал
на обычное слово «подарки» создавали шум и дополнительные repair-проходы.
Правила не менялись между вариантами или по ходу опыта. Доступность всех
инструментов не означает отсутствия ложных срабатываний или полной проверки
смысла. Один прогон на десяти знакомых фрагментах не устанавливает общий
выигрыш качества; между двумя опытами есть вариативность ответов модели.
