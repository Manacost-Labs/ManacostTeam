# Вычёркивание лишнего и рубрика отклонений

Правила расширяют [стандарт игроковой статьи](PLAYER_EDITORIAL_STANDARD.md),
[задание автору](PUBLICATION_CONTEXT.md) и
[контракт отзывов](PUBLICATION_REVIEW_CONTRACT.md). Проверки измеряют исполнение
контракта; ни охват, ни цитаты, ни положительный отзыв не означают одобрения владельца.

## Проход после черновика

Порядок native v4: sources → research → draft → **deletion_pass** → fact_review
→ literary_review → export. После revise, feedback и изменения context проход
повторяется. Полезный текст может остаться целиком: обязательного процента сокращения нет.

Вопрос к каждому предложению: **«Какое решение потеряет игрок, если это убрать?»**
Нет ответа — вычеркнуть. В этом проходе разрешены только удаления и сокращения.
Новые факты, объяснения, связки, слова и перестановки запрещены. Для необходимой
содержательной правки оставьте вопрос следующему ремонту и независимой проверке.

Вычеркните пересказ текста карты/силы героя, уже видимого в подсказке шорткода;
очевидное; страховочную оговорку без пользы; совет, повторённый в другом разделе;
отчёт об источниках в теле («по данным…», «игроки на Reddit…»); статистическое
наблюдение, превращённое в правило без проверяемой причины; сравнение вариантов,
между которыми игрок практически не выбирает. Слабый блок советов удаляется целиком.
«Убрать воду» **не означает сократить полезные объяснения**: необходимые основы
для выбранного читателя, развилки, числа, условия, исключения и уверенность сохраняются.

`next` передаёт четыре диагностики: `card_paraphrase.retelling`,
`owner.overused_word`, `owner.section_repeat`, `owner.forbidden_literal`.
Это вход редактору, а не приказ удалить любой помеченный фрагмент. В полном
EditorTeam расчёт общий с audit. В минимальном stdlib runtime без NLP `next`
честно сообщает `diagnostic_status=unavailable`: запустите полный EditorTeam audit
для исходного draft и передайте находки редактору; пустой массив не означает чистый текст.

Передайте `submit --stage deletion_pass --artifact cuts.json`:

```json
{
  "article_sha256": "хеш исходного draft из next",
  "deletions": [
    {"start": 42, "quote": "Точная удаляемая подстрока", "reason": "Какой лишний повтор убран"}
  ],
  "unchanged_reason": ""
}
```

`start` — индекс Unicode символа Python, не байта/UTF-16. Диапазоны идут по
возрастанию без пересечений. Runner сам применяет удаления, сохраняет исходник,
результат и JSON с причинами в artifacts. Поле нового текста не допускается.
Для `deletions=[]` нужна конкретная причина сохранения. Отчёт не вставляется в статью.
Программа не доказывает, что удалённое было лишним: это проверяют независимые отзывы.

## Обязательная литературная рубрика

`owner_checks` содержит ровно одну строку `{id,status,quote,reason}` по каждой
категории ниже. Статус — `clear`, `issue`, `unverified`. **Каждой** строке нужна
непустая точная цитата текущей статьи, в том числе при проверке отсутствия дефекта;
reason объясняет реальный охват проверки. Цитата для отрицательного результата
сохраняется как фрагмент для ремонта, отрицательный вердикт не заменяется pass.

| id | Что оценивает reviewer |
| --- | --- |
| card_text_retelling | Даёт ли объяснение решение сверх подсказки карты/силы героя? |
| obvious_or_water | Меняет ли фраза выбор читателя? Нужна ли оговорка? |
| weak_or_obvious_tips | Есть ли подтверждённые полезные решения? Нужен ли блок целиком? |
| duplicated_advice | Есть ли новое условие или функция у повтора из другого раздела? |
| source_attribution_in_body | Не попали ли в GUIDE площадки и отчёт о поиске? |
| unsupported_or_false_claim | Не превращено ли observation в правило с выдуманной причиной? |
| illogical_comparison | Доступны ли игроку оба варианта в этой ситуации? |
| unclear_edge_case | Ясно ли, как попасть в частный случай и что он меняет? |
| genre_fit | Подходят ли объём и манера выбранным образцам и теме? |
| ai_tells | Нет ли искусственных рамок и шаблонной интонации? Это не детекция авторства. |

`issue`/`unverified` блокируют допуск. Native сохраняет отрицательный JSON в
истории и выдаёт repair с цитатой. Go превращает accept с отрицательной строкой
в repair и сохраняет `owner_review.<id>` finding; он не просит переписать verdict.
Ошибка формы (нет категории, цитаты, причины) требует исправления отчёта;
содержательная ошибка — исправления статьи. Нельзя подтвердить качество простым
заполнением строк. [owner-eval](../editor/docs/OWNER_EVAL.md) использует те же имена:
прежние метки разметки сохраняются, `reviewer_category` указывает общую категорию.

Для жанра `genre_review` содержит измерения из `owner_review_assignment.genre`
(`article_words`, `examples`, `word_budget`) и собственный reason. Бюджет min/max
выводится из полных выбранных образцов author-context, не из общего корпуса и не
из цитат. Отклонение от диапазона reviewer оценивает по полезному содержанию.
Без полных замеров бюджет неизвестен: не подставляйте фиксированные 440–1300 слов.

## Основание утверждения

`claim_kind=mechanic` допускает правило с «потому что», когда причина подтверждена
механикой и соответствует условиям. `observation` остаётся наблюдением в своей
выборке, без придуманной причины. `opinion` передаётся с именем игрока и лишь при
пользе читателю. Старый claim без поля читается без автоматической классификации.
Если handoff говорит «блок советов писать не из чего», блок не пишется.

## Совместимость и Go

Сохранённые native runs v1/v2/v3 читаются с прежней историей; прежние неполные
отзывы не разрешают новый export. Нужен новый текущий run из сохранённых входов
с проходом удаления и независимыми отзывами. Не исправляйте номер версии вручную.
Export повторно проверяет рубрику, жанровые измерения и воспроизведение удаления.

Go оркестрирует, Python измеряет морфологию (`internal/analyzer/client.go`).
Переносить словари и калибровку в Go не нужно: `/analyze` и `/validate` используют
тот же расчёт owner findings. Postflight передаёт их проходу удаления и критику;
явный запрет требует author-context, как и в audit. В `/v2/edit` собственного
author-context нет: не выдавайте task_context метаданных игры за запреты владельца.

Go при reconstruct/write выполняет отдельный deletion pass после каждого
черновика/ремонта и перед независимыми отзывами. Результат вычисляется только из
точных удалений; receipts возвращаются в `deletion_passes`, вне текста статьи.
При обычной вычитке/facts_only нет полномочий срезать готовую авторскую статью:
критик проверяет все категории и предлагает точечный repair с фрагментом.
Go retrieval хранит отрывки, а не author-context полных образцов; бюджет полной
статьи в этом маршруте неизвестен и не выводится из длины отрывка.

## Диагностика без API

```text
editor-team audit статья.md --profile battlegrounds-article --author-context context.json
editor-team owner-eval <локальный набор> --author-context context.json --format json
```

Наборы владельца и реальные статьи остаются в ignored build/. Тесты используют
синтетику. Для ручного BG-workflow применяются тот же вопрос удаления, отдельный
журнал cuts.json и все десять строк рубрики до сдачи; `check` остаётся диагностикой.
