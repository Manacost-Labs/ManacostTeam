# Качество русской прозы

[Следующий срез: адресный поиск перед генерацией](../../research/deep-research/references/reader-research-loop.md).
В native research подключены задания next/search, в author/prose — меньшая
доля повторов и пустых рамок, больше связности и выразительности. Полезные
условия и оговорки сохраняются; метафоры и выдуманные эпизоды не обязательны.

## Что готово

- [Банк](../evals/examples/review.json): 10 записанных авторских поправок из
  `config/corrections.yaml`; все pending, одобренных примеров пока 0.
- [16 синтетических кейсов](../evals/cases/russian.json): согласование,
  условия, исключения, уверенность, отрицания, роли чисел, названия карт,
  сленг, цитаты, сохранение сильного текста, контекст слова «трекер»,
  шорткоды и терминология Полей сражений.
- Opt-in подбор примеров в существующем `prompt-direct`. Подбор пока
  лексический; BGE для этого банка не измерялся и не подключался.
- Candidate-промпт рассматривает вводные и канцелярские обороты по контексту;
  сохраняет точные цитаты и удачные фрагменты.

Прирост качества статей пока не измерен. WP/Go runtime и модель не переключались.
Агентный авторский путь поддерживает opt-in банк; helper включён в опубликованные
EditorTeam 1.15.3 / Manacost Publish 1.12.2 (общий выпуск 1.20.3).

## Сквозной рабочий путь

На стадии `draft` агентной публикации можно получить задание с примерами:

```sh
# Из editor; профиль примеров должен совпадать с profile текущего run.
.venv/bin/python -m editorteam.publication_run next ../build/my-publication \
  --example-bank ../build/language-bank/approved.json \
  --game hearthstone --editorial-mode GUIDE
```

Этот необязательный режим требует Node.js; без флага путь остаётся прежним.
Canonical Node-selector общий для eval-provider и native task: проверки
approval/split/контекста не расходятся. В задании фиксируются ID и SHA256 банка.
Для подбора используется текущий draft либо brief с принятым chapter_brief;
источники handoff исключаются. Примеры передаются только автору; на стадиях
источников и независимых reviews этот флаг отклоняется. Состояние run не меняется.

После появления реальной редакторской правки сохраните три версии:

```sh
node evals/example_bank.js capture --draft ../build/draft.md \
  --ai ../build/ai.md --final ../build/final.md \
  --source 'путь или URL статьи' --reason 'какую проблему устранил редактор' \
  --game hearthstone --profile guide --mode GUIDE --real-source \
  --out ../build/language-bank/article-001
node evals/example_bank.js verify-capture --input ../build/language-bank/article-001
```

Команда пишет в новый приватный каталог draft.md, ai.md, final.md,
manifest.json с хешами и review.json. Исходные байты, включая CRLF, сохраняются.
Пример учится на AI → final, а черновик остаётся для будущего сравнения.
Это запись кандидата: `approval=null`, human_approved=false. Её наличие
не доказывает, что финальную версию написал или проверил человек. Подтверждение
по-прежнему выполняется отдельно. Подмену snapshot выявляет verify-capture.
Для настоящей оценочной пары используйте сохранённые draft/final и существующий
`pairs.js case` после человеческой проверки. Синтетические capture помечайте
явным `--synthetic`; они не становятся рабочими примерами. Capture требует
ровно один флаг: --real-source или --synthetic. Объявление реального источника
не является подтверждением редакторской проверки. Первоначальный review.json
заморожен целиком, включая причину и контекст; для исправлений и одобрения
используйте новый файл вне capture-каталога. Хеши выявляют частичные изменения,
но не аутентифицируют происхождение: согласованная замена всех файлов и
манифеста требует отдельного защищённого журнала, как в плане production.

Итоговый технический gate, без модельных API-вызовов:

```sh
node evals/russian_stage.js --out ../build/language-stage/status.json --technical-only
```

Он запускает Node-регрессии и тесты native publication, сохраняет результаты
и отдельные статусы банка, модели и human acceptance. Флаг --technical-only
разрешает exit 0 только для технической части. Без него отсутствие human
acceptance даёт exit 2; техническая ошибка — exit 1. Реальный модельный и
человеческий замеры не выводятся из успешных тестов.

## Подтверждение примеров

Стартовые записи — локальные решения из мета-отчёта 36.4, не запреты слов.
Например, замена «трекер» касается описания сбора статистики, а не приложения.
Контекст сохранён, если был в журнале; структурные записи описывают решение,
а не готовый абзац. Источник — закреплённая версия журнала; SHA256 относится
к точным байтам его JSON-экспорта в `build/language-bank/corrections.json`.

Откройте `evals/examples/review.json`, проверьте before/after/reason/context,
игру, профиль, режим и split. Уточняйте их до подтверждения. Сильный пример
может иметь before == after, чтобы показывать обоснованное сохранение текста.
Команду подтверждения выполняет человек после проверки конкретной записи:

```sh
# Из editor. ID взять из review.json; каталог ../build/language-bank существует.
node evals/example_bank.js approve --input evals/examples/review.json \
  --id edit-ID --reviewer owner --attest-human-review \
  --out ../build/language-bank/review-01.json

# Следующий пример: input review-01.json, out review-02.json и т. д.
node evals/example_bank.js export --input ../build/language-bank/review-01.json \
  --out ../build/language-bank/approved.json
```

Выходной файл всегда новый. Без одобренных записей export завершится ошибкой.
Синтетика не экспортируется даже с тестовым подтверждением. Изменение текста,
причины, контекста, источника или split нарушает hash одобрения и требует
новой проверки. Это защита от случайных изменений, не удостоверение личности:
скрипт не устанавливает, кто физически выполнил команду.

Новые фрагменты подготовьте как JSON-массив `{was, became, reason, context,
scope}`. Можно использовать реальные пары; из опубликованной статьи нельзя
выдумывать первоначальный черновик и объявлять его человеческой парой.

```sh
node evals/example_bank.js prepare --input ../build/language-bank/new-edits.json \
  --source 'путь или URL исходного материала' --game hearthstone \
  --profile constructed-guide --mode GUIDE \
  --out ../build/language-bank/new-review.json
```

Игра/профиль/режим описывают все записи входа; разные контексты готовьте отдельно.
Объединять записи можно до подтверждения, сохраняя ID и provenance.
Для синтетики обязателен `--synthetic`. Сохраняйте исходный JSON вместе с SHA256.
Цель — 50–100 проверенных фрагментов, включая удачные неизменённые примеры.
Языковое подтверждение не подтверждает игровые факты; для них остаётся
существующий `publication_benchmark` и публикационные проверки.

## Подбор и сравнение

Подбор ограничен той же игрой, профилем и режимом GUIDE/ANALYSIS/REPORT.
Выбираются до 3 целых примеров с общими словами, каждый до 1800 знаков
вместе с причиной и контекстом. Равные тексты и вложенные фрагменты от
80 знаков исключаются; короткая локальная правка допустима внутри новой статьи.
Объём выбранных примеров — до 5400 знаков плюс JSON-обвязка. Общие слова
считаются по before/after/context; причина отображается как пояснение решения.
Holdout не экспортируется; если часть источника отложена, исключается вся
группа по source или SHA256 входного экспорта. Перед итоговым замером отдельно
проверьте разделение по статьям: лексический фильтр не выявляет все перефразы.
Закрытые материалы не используйте для пополнения банка и настройки промпта.

При известных `source_url`/`source_sha256` передавайте их в vars запроса:
подбор исключит этот источник. При явном `examples: on` нужен
`EDITOR_EVAL_EXAMPLE_BANK` с экспортированным банком. Нет подходящих записей —
ошибка. Без этого флага работает прежний путь.

Готовая конфигурация: `evals/promptfooconfig.russian.yaml`. Она сравнивает
один candidate-промпт и модель: `comparison_variant=baseline` без примеров,
`candidate` с примерами. `example_ids` сохраняет выбор; `style_example_texts`
подключает существующую проверку копирования. Примеры передаются как данные,
только для формы; их игровые сведения не становятся источником статьи.

Живой прогон требует настроенных существующих model/judge endpoints и gateway
`/validate` с полным `/health`; он может расходовать API-бюджет. В этой задаче
живые вызовы модели не выполнялись. До human review стартового банка прогон
с примерами намеренно недоступен. 16 синтетических кейсов — регрессии,
а не итоговая выборка качества.

## Слепая оценка

После настоящего A/B-прогона сохраните Promptfoo result в локальный build,
заморозьте результаты и передайте их в существующий Potato:

```sh
# Из editor. Ключ не попадает в Potato project.
node evals/blind_review.js prepare ../build/language-bank/results.json \
  --out ../build/language-bank/blind --swap-order
python3 evals/potato_review.py export \
  --pairs ../build/language-bank/blind/pairs.json \
  --out ../build/language-bank/potato
```

Запуск UI и импорт — [в инструкции Potato](evals.md#potato-локальная-слепая-оценка-в-браузере).
Общий A/B-протокол проверяет readability, naturalness, usefulness, voice,
conditions, restraint. Для оценки нужны цитаты и причина предпочтения;
незаполненные отзывы остаются pending. Приватные материалы/отзывы храните
вне Git. По [плану приёмки](../../docs/PRODUCTION_READINESS.md): 20 реальных
материалов, 12 для настройки и 8 закрытых, плюс 5 чистых контролей;
одинаковые модель/параметры, контроль фактов и замер ручной доработки.

## Проверки без модели

```sh
node --test evals/tests/*.test.js
node evals/cases/russian.js --check
```

Последняя команда проверяет 16 контролей и 16 испорченных вариантов.
Контракты узкие, лексические, с заданными альтернативами; они не заменяют
смысловую и литературную проверку и не доказывают улучшение модели.

Первый срез 5 ноября 2026: 52 Node-теста; Python gate — 998 passed,
38 skipped, 5 subtests passed (37 пропусков требуют Vale, один — optional
Potato в основном Python-окружении). Ruff, `promptfoo validate`, actionlint,
формат существующих пар и воспроизводимость skill-архивов прошли.
Синтетический экспорт 28 слепых предъявлений в Potato проверен без модели
и без заполнения человеческих оценок. WP/Go проверки не запускались:
их исходники и production не менялись. skillctl/codegraph/Serena здесь
не настроены; использованы локальный профиль, поиск по исходникам и read-only
GPT-6 Luna Scout/review. Реальных пар у владельца пока нет; собирать их нужно
из будущих редакторских правок, сохраняя черновик и финальную версию.

Сквозной срез: 57 Node-тестов, 1000 Python passed / 38 skipped / 5 subtests,
250 корневых тестов; wheel и оба skill-пакета содержат canonical helper,
14 прежних архивов byte-identical. Native selector проверен в распакованных
EditorTeam/Publish, включая отклонение pending-банка; capture/verify проверены
на явно синтетическом материале. Итоговый локальный отчёт:
`build/language-stage/status-final.json` — technical PASSED,
human/model NOT_RUN, реальных пар 0/20. Данные отчёта не заменяют приёмку.
