# owner-eval: аудит на реальных отклонениях владельца

`audit` без ошибок не значит, что владелец примет текст. 9 ноября 2026 года
статью об APM-механизмах вернули больше 20 раз, а аудит каждый раз показывал
«без ошибок». `owner-eval` измеряет, какие из настоящих претензий аудит ловит
без модели, а какие остаются рецензенту.

## Запуск

```bash
PYTHONUTF8=1 editor-team owner-eval build/owner-rejections/apm-2026-11-09
PYTHONUTF8=1 editor-team owner-eval build/owner-rejections/apm-2026-11-09 --format json
# запрет слова из требований владельца проверяется, если передать author-context
PYTHONUTF8=1 editor-team owner-eval <набор> --author-context author-context.json
```

Профиль по умолчанию — `battlegrounds-article`; другой задаётся `--profile`.
На наборе из 28 файлов прогон занимает около полутора минут. Платных
вызовов и сети нет.

Для каждого отклонения прогоняется `audit` по версии **до** исправления.
Статусы:

| статус | значение |
| --- | --- |
| `detected` | каждый размеченный фрагмент помечен находкой подходящего вида |
| `partial` | помечена часть фрагментов |
| `missed` | категория должна ловиться, но ни один фрагмент не помечен |
| `needs_reviewer` | категория без модели не ловится; причина — в поле `reason` |

`unlabeled_hits` — находки нужного вида вне цитат: владелец мог назвать
проблему без цитаты («повтор Портрета в двух разделах»). `other_hits` —
находки других анализаторов на строке фрагмента; они не засчитываются.

Отдельно считаются находки **новых** проверок (`owner.*`,
`card_paraphrase.retelling`) на `gold/*` и на версиях с `accepted` в имени:
претензий к этим текстам нет, поэтому всё найденное там — ложная тревога.

## Набор отклонений

Наборы — рабочие материалы владельца. Они лежат в `build/owner-rejections/`,
который не попадает в Git. В тесты попадают только синтетические тексты.

```text
build/owner-rejections/<тема>-<дата>/
  labels.json      разметка
  versions/*.md    версии статьи; принятая — с accepted в имени
  gold/*.txt|*.md  эталонные статьи, на которые указал владелец
```

`labels.json`:

```json
{
  "schema_version": 1,
  "article": "Название",
  "rejections": [
    {
      "id": "R05",
      "version": "final-v9-backup.md",
      "category": "card_text_retelling",
      "owner": "слова владельца",
      "fragments": ["дословный фрагмент версии"]
    }
  ],
  "accepted": ["final-accepted-candidate.md"]
}
```

- `version` — текст **до** исправления этого замечания.
- `fragments` — дословно из версии. Шорткоды `[hs_bg …]`, `**` и разница
  «е/ё» при сравнении не учитываются. Фрагмент из одного слова («стек»)
  сверяется с цитатой находки, а не со строкой.
- `accepted` — необязательно. По умолчанию это файлы `versions/` с
  `accepted` в имени.
- Категории, которые ловятся детерминированно, и находки, которые им
  засчитываются, перечислены в `owner_eval.DETERMINISTIC`. Категории для
  рецензента с причиной — в `owner_eval.NEEDS_REVIEWER`. Новую категорию
  добавьте в один из этих словарей, иначе она получит `needs_reviewer`
  без причины.

## Набор хороших текстов

Чтобы мерить новые проверки на текстах без претензий (гайд, эталон, принятая
версия), `labels.json` не нужен. Каталог содержит только тексты:

```text
<каталог>/
  *.md, *.txt        хорошие тексты в корне
  gold/*.md|*.txt    эталоны (необязательно)
```

```bash
# гайд по колоде: в этом профиле работают owner.paragraph_starts и owner.forbidden_literal
PYTHONUTF8=1 editor-team owner-eval build/gold-references --profile constructed-guide
PYTHONUTF8=1 editor-team owner-eval build/gold-references --profile constructed-guide --format json
```

Без `labels.json` каждый файл прогоняется один раз. Для каждого файла
выводятся число находок новых проверок `error / review`, разбивка по пяти id
(`card_paraphrase.retelling`, `owner.overused_word`, `owner.section_repeat`,
`owner.paragraph_starts`, `owner.forbidden_literal`), строки находок (стр., id,
цитата) и итог. JSON содержит те же данные: `files[имя].new_checks`,
`files[имя].by_id`, `files[имя].new_findings`, `totals`, `profile`.

Флаг `--profile` задаёт набор проверок. Пять id не равны одному профилю:
`card_paraphrase.retelling`, `owner.overused_word` и `owner.section_repeat`
работают только в профилях Полей сражений (`battlegrounds-guide`,
`battlegrounds-article`); в `constructed-guide` ноль по этим id ничего не
говорит о тексте.

Как читать результат: всё найденное на хорошем тексте — кандидат в ложное
срабатывание. Владелец к этим текстам претензий не имел, поэтому решение
(поправить проверку или оставить находку) принимает редактор. Находка не
доказывает ошибку текста, отсутствие находки не доказывает его качество.

## Что добавлено в audit

Проверки работают в профилях `battlegrounds-guide` и `battlegrounds-article`.
Запрет слова владельцем работает в любом профиле. Однообразные начала абзацев
проверяются ещё и в `constructed-guide`.

| находка | серьёзность | что ловит |
| --- | --- | --- |
| `card_paraphrase.retelling` | review | одно предложение пересказывает текст карты, аксессуара или силы героя |
| `owner.overused_word` | review | существительное встречается в статье во много раз чаще, чем у автора |
| `owner.section_repeat` | review | один и тот же факт или совет в двух разделах |
| `owner.forbidden_literal` | error | слово из `forbidden_literals` в author-context (`audit --author-context`) |
| `owner.paragraph_starts` | review | серия абзацев одного раздела с одним началом: «Название — …» (≥ 10, допускается один посторонний абзац подряд, и в серии не меньше двух записей до 14 слов) или одно первое слово (≥ 6 подряд) |

### Почему пересказ R05/R13 раньше не ловился

1. `card-paraphrase` — отдельная команда. В `audit` она не запускалась.
2. Её порог считался по всему документу: доля пересказа 0,023 при пороге 0,05
   давала «норму», даже когда фраза найдена.
3. В снимке не было текста сил героев Полей сражений. Под именем «Торим,
   владыка бури» лежал текст коллекционной карты. Шорткоды не
   использовались, поэтому «Битбоксер» сопоставлялся с картой Constructed, а не
   с «Притягательным битбоксером».
4. Любое «когда/если» считалось условием совета, поэтому пересказ силы героя
   («…когда вы потратите 60 золотых») не засчитывался.

Теперь в снимке `card_texts_ru.json` есть раздел `bg`: ID → название и
тексты. Для героя хранится текст его силы (`heroPowerDbfId`), для существа —
обычный и золотой тексты. Снимок обновляется штатно:
`editor-team card-paraphrase --update-texts` (HearthstoneJSON, бесплатно).
Шорткод `[hs_bg id="…"]` даёт точную карту. Без шорткода карта ищется по
названию.

### Калибровка (2026-11-10)

Корпуса: `corpus-bg` (45 гайдов), `corpus-archive` (297) и 6 эталонов
владельца.

**Пересказ по предложению:** доля текста карты ≥ 0,5, своих слов ≤ 0,5,
общих лемм ≥ 3; в предложении нет решения, причины или опоры совета.

| порог (доля/свои/общие) | эталоны | corpus-bg | corpus-archive | принятая версия |
| --- | --- | --- | --- | --- |
| 0,5 / 0,5 / 3 (выбран) | 1 фраза в 1 из 6 | 3 в 3 из 45 | 65 в 50 из 297 | 0 |
| 0,5 / 0,6 / 3 | 1 | 5 | 97 | 0 |
| 0,6 / 0,5 / 3 | 0 | 2 | 43 | 0, но теряется R05 |

Находки в архиве — в основном настоящие пересказы в старых гайдах по колодам.
На эталоне сработала одна фраза: «Королева богомолов в начале боя получает
4 баффа…».

**Слово-паразит:** существительное вне словаря игры (названия и тексты
карт). Порог: ≥ 8 раз, ≥ 10 на 1000 слов и в ≥ 100 раз чаще корпуса. Корпус
считается без самого документа. Сработало: corpus-bg — 2 из 45, архив — 3 из
297, эталоны — 0 из 6. «Стек» сработал в 9 версиях APM-статьи: 19 раз на 629
слов, у автора — 0 на 1,77 млн. Частоты лежат в
`corpus_nouns_ru.json`; пересчёт — `editor-team owner-eval --update-frequencies`.

**Повтор между разделами:** пара предложений из разных разделов, ≥ 3 общих
смысловых лемм, коэффициент Жаккара ≥ 0,5. Сработало: эталоны — 1 пара на 6
статей (настоящий повтор состава Exodia), corpus-bg — 3 пары в 1 из 45,
принятая версия — 0. В гайдах по колодам (corpus-archive) — 283 пары в 52 из
297: там разделы по матч-апам повторяют формулы. Поэтому проверка включена
только в профилях Полей сражений.

Слово-паразит проверено и на итоговом коде с поставляемым снимком частот
(документ входит в корпус): corpus-bg — 1 из 45 («тринкета»), архив — 1 из
297, эталоны — 0.

**Однообразные начала абзацев (2026-11-10).** В большом гайде по колоде,
который владелец назвал эталоном, 13 абзацев подряд открывались «Карта — …»,
часть из них пустые. Абзац открывает схема «title»: 1–4 слова с заглавной и
тире в пределах 80 знаков; схема «word» — первое слово. Заголовок, список,
таблица, цитата и маска кода обрывают серию. Анализ чисто текстовый, без NLP, и
работает в минимальном runtime. Пороги подобраны по числам:

| правило (серия «название — …») | corpus-archive (297) | corpus-bg (45) | эталоны (6) | принятая версия |
| --- | --- | --- | --- | --- |
| ≥ 5 подряд, без допуска | 247 гайдов, 460 серий | 14, 30 | 0 | 0 |
| ≥ 8, допуск 1 | 219, 302 | 10, 14 | 0 | 0 |
| ≥ 10, допуск 1 (выбрано) | 171, 211 | 8, 10 | 0 | 0 |
| ≥ 12, допуск 1 | 118, 140 | 7, 8 | 0 | 0 |

Схема «то же первое слово»: ≥ 6 подряд — 5 серий в архиве и 4 в corpus-bg (в
итоговых числах ниже). Выбран порог ≥ 10 с допуском 1: единственный, при котором
гайд-эталон по Раза Охотнику на демонов ловится, а эталоны Полей сражений и
принятая версия остаются чистыми. Итог с выбранными порогами: corpus-archive —
172 из 297 гайдов (216 серий), corpus-bg — 9 из 45 (14 серий), эталоны владельца
и принятая версия — 0. На гайде-эталоне про Раза проверка срабатывает один раз:
`owner.paragraph_starts`, review, стр. 46–88, «11 абзацев открываются схемой
«название — …»», начало серии — первый абзац раздела «Основа колоды»
(«Ледяной осколок — …»). 13 абзацев владельца делятся тремя посторонними
(«Они повсюду выполняет…», «Броксигар, а скорее его части…», «Королевский
библиотекарь почти никогда…»), поэтому нужен допуск 1.

Уточнение при приёмке (2026-11-10): серия «Название — …» сама по себе — форма
автора, она срабатывала на 172 из 297 гайдов архива (58 %), и такой сигнал
редактор перестал бы читать. Теперь серия отмечается, только если в ней не
меньше двух пустых записей — абзацев до 14 слов («ключевое заклинание, без него
колода существовать не может»). В находке цитируются именно они. Итог с этим
условием: corpus-archive — 52 из 297 гайдов (47 по схеме «название», 5 по
первому слову; 58 серий), corpus-bg — 4 из 45, эталоны владельца и принятая
версия — 0. На гайде-эталоне про Раза проверка срабатывает один раз (стр. 46–88,
11 абзацев, 2 пустые записи: про Жар души и Эредара-обманщика).

Ограничение остаётся: длина записи не доказывает, что она пустая, а длинная
запись может быть пересказом. Находка отправляет автора проверить короткие
записи серии: есть ли роль или условие. Проверка не включена в мета-отчёты,
новости и аналитику.

**Запрещённое слово:** одиночное русское слово ловится во всех падежах
(«стека», «стеком»), но не внутри другого слова («стеклянный»). Фраза из
нескольких слов сверяется дословно. Это правило общее с publication run
(`publication_context.literal_errors`).

**Не добавлено: плотность страховочных оговорок (R04).** Учитывались слова
«почти», «обычно», «может», «еще не повод» и подобные. Версия v8, которую
вернули за «мусорный текст», даёт 8,6 на 1000 слов. Медиана corpus-bg — 8,7,
p90 — 12,3, у эталонов — до 14,6. Порог, который ловит v8, сработал бы
на половине гайдов автора, поэтому оценка оставлена рецензенту.

## Рубрика reviewer и диагностика

Для гайда по колоде (`article_plan.genre = "deck_guide"`) к десяти категориям
добавлены `advice_has_condition_and_reason`, `mastery_has_threshold_or_order`,
`term_before_definition`; все три остаются в `NEEDS_REVIEWER`: наличие условия и
причины, перенос порога и порядка из карточки опыта и порядок объяснения
терминов — оценка смысла, а не поиск слов. Детерминированно страхуются только
порядок разделов в плане (`role: mechanics` в `depends_on`) и серия однообразных
начал (`owner.paragraph_starts`; категория разметки `uniform_openings`).

[Проход удаления и рубрика](../../docs/OWNER_REJECTION_LOOP.md) принимают четыре
находки audit как вход. `audit --author-context` работает с `--task-context` через
server.analyze; те же находки возвращаются через `/validate` для postflight Go.

`reviewer_category` сопоставляет старые метки с общей рубрикой:
water_hedging/obvious_fact → obvious_or_water;
source_attribution_overuse → source_attribution_in_body;
genre_mismatch_too_long_literary/too_short_weak_heroes → genre_fit;
section_rejected_structure → weak_or_obvious_tips; duplication → duplicated_advice.
Исходная category и результаты измерения сохраняются. Рубрика не превращает
needs_reviewer в автоматически пойманное отклонение. Проверки охвата и цитат
не измеряют качество на реальных статьях; живого reviewer-прогона не было.
