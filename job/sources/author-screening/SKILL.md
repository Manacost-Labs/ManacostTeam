# Отбор игрового автора

У скилла два режима. Определи, какой нужен, по первому сообщению.

**Режим «Составить тест»** — пользователь просит задания, тест, анкету. Работай по разделу «Составление теста».

**Режим «Проверить ответы»** — пользователь прислал ответы кандидата, ссылку на них или просит оценить человека. Работай по разделу «Проверка ответов». Не составляй новый тест, если об этом не просили.

Если режим неясен — спроси одной фразой, не разворачивая опросник.

---

## Что вообще проверяется

Пять шкал, полное описание с калибровочными якорями — в `references/evaluation.md`:

| Шкала | Лечится обучением? |
|---|---|
| Понимание игры | Нет |
| Собственная мысль | Почти нет |
| Умение зацепить | Частично |
| Язык | Да |
| Достоверность | Это факт, а не навык |

Последняя колонка определяет всю логику найма. **Корявый язык при сильном понимании игры правится за три-пять материалов с обратной связью. Обратное не правится никогда.** Соблазн взять гладко пишущего кандидата велик, но из таких получаются пересказы патчнотов, ради которых читатель не вернётся на сайт.

## Составление теста

### Шаг 1 — уточни контекст

Направление (Арена / Поля сражений / Стандарт / Вольный / новости / сюжет и лор — либо нестандартное, тогда см. «Нестандартное направление» в `question-design.md`), уровень автора, объём материалов. Если пользователь уже дал это в разговоре — не переспрашивай.

### Шаг 2 — ОБЯЗАТЕЛЬНО проведи ресёрч

Не пропускай никогда, даже если игра кажется знакомой. Порядок действий и реальная доступность источников — в `references/sources.md`. Кратко: патчноуты и терминология — hs-manacost.ru (через сниппеты выдачи) и англоязычные патчноуты Blizzard; **мета и архетипы — собственный API kolodahearthstone, `references/meta-api.md`** (запасные: hearthstone-decks.net, vicioussyndicate, hsreplay); лор — hearthstone.wiki.gg и warcraft.wiki.gg.

Без свежих данных тест получится про прошлый сезон, и это заметит любой играющий человек — доверие к площадке пропадёт с первой строки.

### Шаг 3 — сними состояние меты через API

`references/meta-api.md`: каталог архетипов, винрейты, популярность, матчапы и история после патча одним JSON. Оттуда берутся топ-архетип для задания на мулиган и настоящая цифра для задания на заголовок. Обязательно проверяй блок `meta` в ответе: при `stale` или `cached_after_failure` цифра в тест не идёт без указания даты снимка. Если домен не разрешён в настройках сети — сообщи об этом пользователю одной строкой и работай по запасным источникам.

### Шаг 4 — проверь каждое русское название

Пайплайн — в `references/card-names.md`: официальная локализация из данных HearthstoneJSON (репозиторий hsdata) достаётся программно и закрывает почти все случаи. Если название не подтвердилось — действуй по «Протоколу непроверенного названия» из `sources.md`, а не выбрасывай тему молча.

### Шаг 5 — собери задания

Приёмы и заготовки по направлениям — в `references/question-design.md`. Читай этот файл до составления вопросов.

Тест состоит из двух этапов. **Этап 1 обязателен для всех, этап 2 выдаётся только тем, кто прошёл первый.** Так устроено не из вежливости: итоговая работа стоит кандидату несколько часов, и просить её у всех подряд — значит потерять сильных людей на входе и утонуть в чтении заведомо слабых текстов.

### Этап 1 — отсев, 25–35 минут

| Задание | Основная шкала | Объём |
|---|---|---|
| Быстрый фильтр | Понимание игры | 3 вопроса |
| Своя колода и своя ошибка | Достоверность | список + 200 слов |
| Разбор своей сборки | Понимание игры | 150 слов |
| Чтение меты | Понимание игры | 150 слов |
| Практическое решение (мулиган, матчап) | Понимание игры | 120 слов |
| Мнение по спорному вопросу | Собственная мысль | 120–150 слов |
| Заголовки и лид | Умение зацепить | 3 заголовка + 40–60 слов |
| Правка канцелярита | Язык | 1 предложение |

**У каждого задания этапа 1 ровно одна основная шкала.** Если задание тянет три сразу, при слабом ответе непонятно, что провалено, и профиль теряет смысл.

Блок про мету и колоду (три задания подряд про его сборку, состояние меты и конкретный матчап) — ядро теста для игровых направлений. Формулировки и что в них смотреть — в `question-design.md`, раздел «Мета и колода».

### Этап 2 — итоговая работа, 700–1000 слов

Полноценный материал про колоду или стратегию: то, что кандидат реально будет писать на сайте. Это **единственное задание, которое оценивается сразу по всем пяти шкалам**, и единственное, где снят лимит объёма.

Правила выдачи и оценки — в `question-design.md`, раздел «Итоговая работа». Ключевое:

- выдаётся **после** проверки этапа 1, персонально, с темой, привязанной к его же колоде из задания 1;
- срок 3–5 дней, дольше не надо: работа не должна превращаться в проект;
- при расхождении оценок между этапами доверяй этапу 1 — дома пишут с нейросетью, на коротких заданиях с личной конкретикой это не работает.

**Проверь покрытие перед выдачей:** каждая из пяти шкал должна быть основной хотя бы у одного задания этапа 1. Итоговая работа покрытие не закрывает — она проверяет то же самое ещё раз, в боевом формате, а не вместо.

### Шаг 6 — прогони тест через три проверки

**Узнаваемость.** Узнает ли предмет каждого вопроса за три секунды человек, который играет каждый день? «Какую карту ослабили внеплановым патчем?» — узнаёт. «Чем отличается механика переодевания?» — нет, так её никто не называет в разговоре. Сомневаешься — действуй по протоколу непроверенного названия: непонятный вопрос хуже отсутствующего.

**Разделяющая сила.** Может ли слабый кандидат ответить на вопрос так же хорошо, как сильный? Если да — вопрос бесполезен. Особо проверяй блок 0: там легко скатиться и в очевидное, и в гуглимое — как строить негуглимый фильтр, описано в `question-design.md`.

**Проходимость.** Уложится ли сильный кандидат в заявленное время? Мысленно напиши ответы сам и посчитай. Тест, который нельзя пройти за полчаса, не проходит никто.

### Шаг 7 — оформи двумя файлами

По шаблону `assets/test-template.md`: `test-candidate.md` (только задания) и `test-answers.md` (ключ, критерии, матрица устаревания, таблица источников). В конце обязательно покажи пользователю в чате таблицу источников и матрицу устаревания — он играет в эту игру и проверит за секунды.

## Проверка ответов

Полная процедура, якоря и шаблон профиля — в `references/evaluation.md`. Читай его перед началом проверки. Кратко:

1. **Проверь факты по источникам.** Кандидат может уверенно написать неправду. Названия карт прогоняй через `card-names.md`, а утверждения про мету и «нестандартные карты» в его списке — через API (`meta-api.md`: каталог архетипов и `archetypes/analysis` с картами архетипа). Ошибка в факте — минус к пониманию игры, а не к языку.
2. **Поставь оценки по пяти шкалам, каждую с цитатой** из ответа. Оценка без цитаты — впечатление, а не оценка, и пользователь не сможет её оспорить.
3. **Выдай профиль** по шаблону.
4. **Дай решение и первый шаг** — не «брать / не брать», а на какое направление ставить и что править в первых материалах.

**Не усредняй оценки.** Шкалы неравноценны, средний балл бессмыслен. Работают пороги: понимание игры ниже 5 — отказ при любом остальном профиле; достоверность ниже 4 — отказ; слабый язык при сильном понимании — берём.

**Профиль отвечает не только на «брать», но и на «куда ставить».** Кандидат с высоким пониманием и слабой подачей идёт на гайды, с сильной подачей и средним пониманием — на новости. Отказывать тому, кто силён в чём-то одном, — типичная ошибка.

---

## Железное правило про названия

**Никогда не называй карту, героя, механику или ключевое слово по памяти.**

- Русская локализация не совпадает с калькой с английского.
- Карты ротируются: то, что было в прошлом сезоне, может уже не существовать.
- Механики переименовываются и меняют работу между патчами.

Каждое название в тесте должно быть найдено в источнике в рамках текущей сессии — в первую очередь через пайплайн `card-names.md`. Если не подтвердилось нигде — «Протокол непроверенного названия» в `sources.md`: переформулировка через механику или отказ от темы с фиксацией в отчёте.

---

## Защита от нейросети

Кандидаты будут пользоваться AI. Тест должен быть устроен так, чтобы это не работало:

- **Свежесть** — вопросы про сезон, которому меньше двух месяцев.
- **Личный опыт** — задание, требующее номера хода, маны, состава доски.
- **Живой спор** — вопрос, по которому сообщество ругается прямо сейчас (с зафиксированным источником).
- **Проверяемый артефакт** — свой список колоды, скриншот профиля с рейтингом.
- **Негуглимый фильтр** — блок 0 спрашивает следствия фактов, а не факты.

При проверке ответов признаки генерации идут в шкалу «Достоверность», а не в отдельный вердикт.

---

## Формат вывода

Тест — три markdown-файла по шаблону: задания этапа 1 для кандидата, ключ для редактора и отдельный файл с итоговой работой (выдаётся только прошедшим этап 1). Профиль кандидата — прямо в чат, файл создавай только если кандидатов несколько и нужно сравнение.

Если тест пойдёт на сайт, предложи выгрузить вопросы в JSON: тип, текст, лимит по словам, варианты и правильный ответ для автопроверяемого блока. Без запроса не делай — лишний артефакт мешает.

## Справочные файлы

- `references/sources.md` — где проверять состояние игры, реальная доступность площадок, протокол непроверенных названий. Читать до составления вопросов.
- `references/card-names.md` — пайплайн проверки русских названий через данные HearthstoneJSON. Читать до составления вопросов и при проверке ответов.
- `references/meta-api.md` — собственный API kolodahearthstone: архетипы, винрейты, матчапы, проверка свежести данных. Читать до составления вопросов о мете.
- `references/question-design.md` — приёмы и заготовки по направлениям, включая Вольный и негуглимый блок 0. Читать до составления вопросов.
- `references/evaluation.md` — шкалы, якоря, шаблон профиля, решающие правила. Читать до проверки ответов и при подборе заданий.
- `assets/test-template.md` — структура двух файлов теста, матрица устаревания, отчёт об источниках.
